# GPT-5.6 vNext 混用检测器

这是一个面向 OpenAI-compatible API 中转服务的本地检测工具。它不要求你提供“可信 API”，而是通过 Juice、固定输出、提示覆盖检查和经过可信三模型标定的行为分布，寻找 GPT-5.6 Sol、Terra、Luna 或旧型号被混用的证据。

> 当前版本：`4.0.0`
>
> 适合发现：固定或按比例混用、输出替换、简单 Juice 隐藏覆盖、只在特定请求格式或短上下文中给真模型。
>
> 不能证明：上游绝对没有透明代理、没有识别探针、没有只对普通业务请求差异化路由。

## 先看最短用法

### Windows

1. 安装 Python 3.10 或更高版本。
2. 解压发行包。
3. 双击 `Windows一键启动.bat`。
4. 浏览器打开启动窗口显示的本机地址，通常是 `http://127.0.0.1:端口/`。
5. 填写待测 API 地址、模型名和 API key。
6. 先选“单次检测”和“低”，点击开始。

### macOS / Linux

```bash
chmod +x start_detector.sh
./start_detector.sh
```

服务只监听 `127.0.0.1`。页面、SQLite 状态和报告都留在本机。

## 第一次该选哪个档

| 档位 | 单次请求数 | 主要内容 | 适合场景 |
|---|---:|---|---|
| 低 | 14 | high/low Juice、32/48 输出完整性、简单提示覆盖 | 先快速排查，成本最低 |
| 中 | 64 | 更多 Juice 档位、国家分布、B80 字符题 | 日常较完整检查 |
| 高 | 202 | 全部内置探针、普通/Native Codex 两种格式、无历史/固定 32K 两种上下文 | 怀疑选择性路由或准备留证 |
| 自定义 | 页面实时估算 | 用户自行改请求次数、探针、格式、上下文 | 研究和复核 |

请求数是逻辑请求数；发生可重试网络错误时，一个逻辑请求最多再重试 2 次。高档中的固定 32K 请求会消耗明显更多输入 token，页面会单独估算这部分成本。

修改任一内置参数后，档位会自动变为“自定义”。报告会显眼标注“自定义档位测试结果仅供参考”，因为它不再满足冻结预设的整体验证条件。可随时点击重设恢复默认值。

## 检测器在检查什么

### 1. Juice 型号指纹

模型的加密状态会暴露一个与思考档位相关的 Juice 数值。检测器不会要求模型生成新数值，而是用恒等计算让最终答案仍等于原始 Juice，例如先乘 2 再除 2。

检测器先按你申报的型号判断。如果答案符合申报型号，即使该数字与其他型号共享，也算当前型号成功；只有“不符合申报型号，却明确符合另一个已知型号”才标记混用。这避免把 Sol、Terra、Luna 在低档或中档共享的 `8`、`16` 误报成混用。

当前还识别 GPT-5.5、GPT-5.4 和 GPT-5.4-mini 的已知 Juice 指纹。命中这些旧型号也会在报告中说明疑似混入的型号。

Juice 是强确定性证据，但它容易被中转针对性伪造，所以不能单独证明上游真实身份。

### 2. 输出完整性

检测器会要求模型只输出固定的 `48` 或 `32`。只要请求成功但原始结果不是与目标完全相同的字符串，就视为严重异常。这层用于发现中转在输出端把 Luna/Terra 特征数值替换成其他数字。

### 3. Juice 提示覆盖

检测器在 developer 消息中显式定义一个随机合成值 `N`，再要求模型做结果仍等于 `N` 的恒等计算。`N` 会避开所有已知 Juice 数值及 `8`、`16`、`40` 开头的长数字。

- 精确返回 `N`：通过本次覆盖检查。
- 返回 `40` 或 `40...`：明确命中隐藏覆盖，严重报警。
- 返回其他已知 Juice 指纹：疑似忽略显式定义，严重报警。
- 其他结果：记为不确定，不凭这一条强行判定型号。

这只能检查简单的语义覆盖，不能证明模型完整披露了所有系统提示。

### 4. 概率行为指纹

内置概率层使用三个固定题面：

- 固定随机国家。
- 固定随机鸟。
- `Count the letter r in strawberry. Reply only with the integer.`

这些题面本身就是指纹的一部分，不能随意改写。检测器将待测端在窗口内的答案分布，与可信 Sol、Terra、Luna 的多时间窗冻结基线比较，输出三模型的相对匹配概率、误差门禁、混合比例和证据不足原因。

这里的“概率”是“在这三个可信基线中更像谁”的条件概率，不是模型真实身份的绝对概率。

## 为什么有两种格式和两种上下文

高档会组合以下选项：

- `normal`：项目自己的普通流式 Responses 请求。
- `native_codex`：复现本项目本地抓包并清理个人字段后的 Native Codex 请求轮廓。
- `no_history`：没有伪造历史的短上下文。
- `fixed_32k_history`：前置 128 条固定消息，形成约 32K 的长上下文。

四种组合用于发现“只对某种客户端格式给真模型”或“只在会话第一次/短上下文给真模型”的路由策略。Native 模式复现的是本项目审计过的固定抓包轮廓，不声称在所有系统和未来版本上都与任意 Codex 客户端逐字节相同。

## 怎样看最终结论

正式报告只有五个主标题：

| 主标题 | 大白话解释 |
|---|---|
| 通过 | 已启用的确定性层通过；启用正式概率层时，其证据也通过门禁 |
| Juice混用 | Juice 命中其他型号，或 32/48、提示覆盖出现确定性严重异常 |
| 仅概率探针混用 | Juice 通过，但冻结概率基线支持纯替换或混合路由 |
| Juice通过但概率探针证据不足 | Juice 没发现混用，但概率样本不足、漂移、未知输出或门禁未通过 |
| 可能非GPT | 每个已启用 Juice 档位都有足够有效请求，却全部无法识别为已知 GPT Juice |

如果 Juice 数据本身不足，例如某个已启用档位完全没有成功请求，检测器不会硬凑第六种结论，而是显示“未形成正式结论”和具体缺口。

严重结论会粘住当前会话。后续一轮恢复正常也不会自动抹掉已经出现过的严重异常，避免间歇性混用被滚动窗口覆盖。

### 网络错误怎么算

超时、连接失败和不完整流只影响线路质量与样本完整性，不直接算模型混用。数据不够时系统会弃权或提示证据不足，而不是把网络差误报成型号差。

## 单次检测与持续监控

## 本地回归验证

项目现在附带离线回归测试，不会访问任何中转站，也不会读取 API 密钥。修改检测逻辑后，在项目根目录运行：

```bash
python -m pytest -q
```

测试覆盖 Juice 共享值与最小有效样本门禁、候选请求的声明模型透传、固定历史上下文顺序、正式概率证据不足时的结论，以及 Windows 默认 Python 运行时的模块导入。若测试未通过，不应据此进行新的中转站判定。

## 三层检测：API 指纹、Agent 轨迹、路由漂移

当前版本额外提供 `/agent` 本地页面和四个本地 API：

- `/api/agent/score`：对一条 Agent 轨迹做确定性评分，只检查工具序列、随机 nonce 和最终状态，不采信模型自报身份。
- `/api/agent/baseline`：从可信端点采集同一产品档位、客户端、协议、上下文和基线版本的 Agent 基线。
- `/api/agent/identify`：将同一 profile 的轨迹同时对比多个模型基线；多模型都匹配时返回 `ambiguous`，不强行归因。
- `/api/routing/analyze`：在相同 profile 内统计模型行为标签的次级占比和窗口间 JS 漂移。
- `/api/three-layer/report`：合并 API 指纹、Agent 轨迹和路由漂移三层结果。

`profile_key` 固定由以下字段组成：`product_tier|client|protocol|context_mode|baseline_version`。其中 `product_tier` 支持 `team`、`k12`、`plus`、`pro`，也兼容常见笔误 `taem`。不同档位、客户端或上下文不得共用基线，否则统计结论没有可比性。

Agent 轨迹检测不是直接让模型回答“我是什么模型”，而是要求它完成带随机 nonce 的多步工具任务，再由本地程序验证最终状态。任务成功只能说明该 Agent 轨迹与某个同环境基线一致，不能单独证明上游模型身份。

### 单次检测

单次模式会先冻结完整任务清单，再用有界并发执行。默认并发为 8，可调范围为 1–32。任务完成后生成一次性报告。

### 持续监控

持续模式每轮先独立抽签决定启用哪些探针，再冻结本轮任务清单。每个探针都有自己的触发概率和滚动窗口：

- 低档：每 150–210 秒一轮，high Juice 每轮必测。
- 中档：每 240–360 秒一轮，加入部分概率探针和更多 Juice 档位。
- 高档：每 480–720 秒一轮，加入全部格式、上下文和内置概率探针。

随机间隔和独立抽签均在每轮重新产生。进程意外退出后，恢复的是已冻结但未完成的任务，不会重新抽签改变历史任务。

## 中断、重试与恢复

每个逻辑任务有稳定的 `job_id`。运行状态写入 SQLite，而不是只放在内存里：

- 成功任务不会重复发送。
- 默认最多 3 次 HTTP 尝试，重启不会重置预算。
- 崩溃遗留的 `running` 尝试会在恢复时对账。
- 单次和持续检测都可从未完成任务继续。
- 探针生成器也使用相同的持久化恢复思路。

启动器会扫描本机运行目录并恢复最近会话。恢复 API 请求仍需要你重新输入 key，因为 key 从不写入 SQLite。

## 完整请求/响应留存

留存默认关闭。开启后必须填写一个绝对路径，检测器会写入：

- 完整请求正文。
- 上游完整原始流式响应。
- 时间、请求 ID、脱敏 URL、请求格式、上下文模式、模型、思考档位。
- HTTP 状态、延迟、首事件时间、事件数、解析结果与错误分类。
- 每条记录的 SHA-256、索引和完整性清单。

认证头和 API key 永远不会写入留存。URL 查询参数会脱敏。但题面、32K 上下文和模型完整输出可能包含敏感内容，因此只应写入受控目录。程序会拒绝临时目录和公开发行目录等明显危险位置。

## 概率探针生成器

页面右上角可进入独立生成器。它只用于建立自定义可信分布，检测器本身不需要可信 API。

推荐流程：

1. 填写可信 API、三个可信模型名和固定题面。
2. 尽量要求极短、易归类的答案。
3. 先用默认单时间窗做可行性测试。
4. 运行后查看每个模型的采样数、有效数、缺失模型和参考 `S / D / tau / w`。
5. 导出探针 JSON，再导入检测器。

单时间窗可以生成、分析和导入，不再强制等待三个时间窗。多时间窗更适合研究跨时间稳定性，但耗时更长。

本版本所有导入的自定义探针都只是参考证据：它们会发请求、显示分布和相对概率，但不能改变正式“通过/混用”结论。原因是任意用户探针尚未经过与内置三探针相同的联合标定，直接加入硬判定会增加误报风险。

## API key 和本地数据

- API key 只存在于当前服务进程内存，以及 Native 子进程的临时环境变量。
- key 不写入 SQLite、报告、日志、留存索引或探针文件。
- 浏览器页面只连接本机服务。
- SQLite、报告和生成器产物保存在发行目录旁的运行目录中。
- 公开包不包含任何监控报告、缓存、个人配置、凭据或内部 Juice 模板。

不要把完整运行目录直接上传到公开网站。需要分享时，只分享你审查过的报告或由构建脚本生成的发行包。

## 公开包与内部包

两个包使用同一检测器、同一概率基线和同一判定逻辑。区别只有 Juice 运行模板池：

- 公开包：3 条公开恒等模板，可直接运行和审计。
- 内部包：使用额外的私有冻结模板池，提高公开关键词过滤的成本。

模板保密只能增加针对成本，不构成密码学安全。报告中始终会说明 Juice 可以被伪造。

## 常见问题

### 为什么低档通过，高档反而证据不足？

高档覆盖更多格式、上下文和概率单元，需要更多有效响应。某一路由不支持 Native 格式、长上下文失败或概率输出落到未知类别，都可能让高档选择弃权。先查看报告的失败项和线路质量，不要只看标题。

### 为什么改了请求次数就变成自定义？

内置档位是按完整参数哈希冻结的。请求数、并发、探针、格式、上下文或持续概率任一变化，都不再是已经验证的预设组合，所以只能给参考结论。

### 为什么概率显示 100.000%，仍可能证据不足？

概率是条件相对值。系统还要检查样本是否完整、输出是否在可信支持域内、时间窗回放错误率上界、覆盖率和混合报警误报上界。门禁不通过时，即使相对概率很尖锐，也不会升级成正式结论。

### 为什么不再使用 COT/加密思维链比较？

旧方案需要额外可信端，增加了使用门槛；较大的窗口又容易把偶发差异误判。当前正式路径已经移除 COT，只保留无需可信端的确定性探针和预先冻结的概率基线。

### “通过”能证明什么？

只能说明本次已启用的检测条件下，没有观察到达到门槛的混用证据。它不能排除透明代理、探针识别、普通请求差异化路由或对已公开模板的专门伪装。

## 最后提醒

- 加密状态层不能仅凭自身区分所有 Sol/Terra/Luna 情况。
- Juice 是可被中转伪造的辅助指纹，即使它在当前确定性层中权重很高。
- 概率探针只对冻结题面、归一化器、档位、格式和上下文契约有效。
- 综合通过不能排除透明代理、探针识别或普通请求差异化路由。
